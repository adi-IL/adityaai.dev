# The Invariant Problem in Autonomous Remediation: Why Code Synthesis Fails Without Closed-Loop Verification

*Generating a patch that silences a crash is easy. Guaranteeing that the patch does not break downstream invariants, truncate valid protocols, or leak resources is hard. Here is an architectural framework for closed-loop verification that bridges the semantic failure gap.*

---

## The synthesis illusion

Autonomous vulnerability remediation has entered production systems. With the rollout of platforms like Google CodeMender, DARPA's AI Cyber Challenge (AIxCC), and benchmarks like CWE-bench, the industry has realized an unexpected reality:

**Vulnerability discovery is computationally cheap. Patch synthesis is straightforward. Patch verification is the real technical barrier.**

Frontier models can inspect an AddressSanitizer (ASan) report, locate a buffer overflow, and emit a plausible git diff in under 15 seconds. The patch compiles cleanly and silences the proof-of-concept crash.

However, empirical evaluations across real-world codebases reveal a concerning statistic: **between 20% and 40% of LLM-generated patches that pass existing automated test suites are semantically broken.**

They truncate valid inputs, introduce silent memory leaks, bypass authentication boundaries, or introduce fresh denial-of-service vectors. An autonomous agent that deploys unverified patches directly to production will degrade system stability.

```
       [ Vulnerable Program State Space ]
       +--------------------------------+
       |   Valid Inputs (Invariants)    | <--- Must Remain Unchanged
       +--------------------------------+
       |   Edge Cases / Protocol Flaws  | <--- LLMs Frequently Truncate
       +--------------------------------+
       |   PoV Attack Space (Exploit)   | <--- Must Be Blocked
       +--------------------------------+
```

To build reliable remediation systems, architects must treat synthesized code as untrusted input. We must construct **closed-loop verification harnesses**.

---

## The five failure modes of synthetic patches

In post-competition analysis from DARPA's AIxCC, researchers analyzed 145 patches generated by frontier models across 63 challenges. In every case, the patch compiled cleanly and passed the repository's build-time unit tests. Yet every patch was rejected upon deeper inspection.

Five systematic failure modes explain why:

```
+---------------------------------------------------------+-------+
| Failure Category                                        | Count |
+---------------------------------------------------------+-------+
| Functionality altered or broken                         |  55   |
| Patched the symptom instead of the root cause           |  38   |
| Incomplete or insufficient guard                        |  28   |
| Wrong API or trust boundary confusion                   |  15   |
| Wrong security mitigation strategy                      |  15   |
| Controversial semantic interpretations                  |   4   |
+---------------------------------------------------------+-------+
```

### 1. Symptom patching vs. root-cause elimination

Models default to patching where the program crashes rather than where the corrupt state originates.

If a function throws a null pointer exception or an out-of-bounds write at line 480, the model inserts a defensive check or doubles the buffer size at line 479. The faulty index calculation at line 120 remains untouched. The moment the program receives an alternate input path that reaches line 480, it either reads garbage memory or fails downstream.

### 2. Input space truncation (domain over-constraining)

When repairing network parsers or serialization libraries, models routinely fix buffer overflows by rejecting any payload exceeding an arbitrary length.

In protocol parsers (such as HTTP/2 framing or DNS dissection), this results in dropping valid packets that carry optional extensions or variable headers. The exploit is blocked, but valid client traffic is rejected, turning a vulnerability into a permanent denial of service.

### 3. Resource lifecycle bypass

To fix use-after-free bugs or state corruption, models frequently inject early `return` or `goto` statements.

While this avoids the dangerous code path, it frequently skips clean-up logic located at the bottom of the function. The patch eliminates the vulnerability while introducing silent memory leaks, unreleased database connections, or locked mutexes that eventually crash the service under load.

### 4. Trust boundary confusion

Models struggle to differentiate between trusted internal buffers and attacker-controlled payload fields.

In packet analysis challenges, models frequently attempted to validate packet boundaries by checking `packet.reported_length` (a header integer supplied by the untrusted sender) instead of `packet.captured_length` (the actual byte length in memory). The code appeared logical to static review, but remained trivial to bypass.

### 5. Concurrency degradation

When attempting to resolve race conditions, models frequently wrap execution blocks in coarse global locks or replace asynchronous calls with synchronous blocking routines. This converts O(1) concurrent lookups into O(N) bottlenecks, causing thread starvation in production.

## The closed-loop verification pipeline

A production remediation harness cannot rely solely on the test suite that accompanied the vulnerable codebase. Existing tests rarely cover the edge conditions exposed by a zero-day vulnerability.

Real verification requires a multi-stage defensive pipeline:

```
                  +--------------------------------+
                  |  Vulnerability PoV & Context   |
                  +--------------------------------+
                                  |
                                  v
                  +--------------------------------+
                  | Multi-Candidate Generation     |
                  |     (Ensemble Size N = 3)      |
                  +--------------------------------+
                                  |
                                  v
+--------------------------------------------------------------------+
|                CLOSED-LOOP VERIFICATION PIPELINE                   |
|                                                                    |
|  1. Compilation & Deterministic PoV Replay (Fail-to-Pass Gate)     |
|                               |                                    |
|  2. AST Semantic Diff & Invariant Extraction (ast-grep, LLVM/SVF)  |
|                               |                                    |
|  3. Dual-Execution Differential Testing (Observational Equivalence)|
|                               |                                    |
|  4. Property-Based Directed Fuzzing (ASan/MSan/UBSan + Invariants) |
|                               |                                    |
|  5. Contrast-Based Candidate Selection                            |
+--------------------------------------------------------------------+
                                  |
                                  v
                  +--------------------------------+
                  | Canary Deployment & Telemetry  |
                  | (Auto-Rollback on Metric Drift)|
                  +--------------------------------+
```

### Stage 1: The deterministic fail-to-pass gate

Before any code modification begins, the harness must reproduce the crash using a minimal proof-of-concept (PoC) payload in an isolated sandbox.

A patch must pass two baseline criteria:
1. **The exploit must fail:** Executing the PoC against the patched binary must return a clean error code without crashing or tripping sanitizers.
2. **The test suite must pass:** All pre-existing unit and integration tests must clear with zero regressions.

### Stage 2: AST structural invariant checks

Before spending compute on dynamic testing, the harness runs static analysis over the synthesized diff using tools like `ast-grep` or Tree-sitter:
- **Reject empty handlers:** Any patch that introduces empty `catch` blocks or ignores return codes is discarded.
- **Enforce lock balance:** Any code path that acquires a lock or allocates memory must maintain an equivalent release along all exit paths.
- **Verify sink reachability:** Ensure critical auditing or logging calls remain reachable.

### Stage 3: Dual-execution differential testing

Dual execution verifies **observational equivalence**. The harness executes the unpatched binary $P$ and the patched candidate $P'$ concurrently inside isolated micro-containers.

A corpus of thousands of historical production requests and benign test cases is sent to both binaries simultaneously:

```python
def verify_differential(unpatched_binary, patched_binary, benign_corpus):
    """
    Ensure the patched binary behaves identically to the original
    on all valid, non-exploit inputs.
    """
    for test_input in benign_corpus:
        res_orig = sandbox_exec(unpatched_binary, test_input)
        res_patch = sandbox_exec(patched_binary, test_input)
        
        # Original binary succeeded; patch must not break it
        if res_orig.exit_code == 0:
            if res_patch.exit_code != 0:
                return False, f"Regression on benign input {test_input.id}"
            if res_orig.stdout != res_patch.stdout:
                return False, f"Output divergence on input {test_input.id}"
            if res_orig.state_checksum != res_patch.state_checksum:
                return False, f"Side-effect invariant violation: {test_input.id}"
                
    return True, "Observational equivalence verified"
```

If the original program returns `200 OK` with valid data and the patched binary returns `400 Bad Request` or an error, the patch has broken an existing operational invariant. It is rejected immediately.

### Stage 4: Property-based directed fuzzing

Passing the single PoC payload does not prove the vulnerability is resolved. It only proves that one specific input has been mitigated.

The harness instruments the binary with AddressSanitizer (ASan) and UndefinedBehaviorSanitizer (UBSan), seeds LibFuzzer or AFL++ with the original exploit payload, and executes directed fuzzing against the modified basic blocks for 10 to 15 minutes.

If the fuzzer discovers any crash or sanitizer violation within the modified code region, the patch is flagged as an incomplete guard and returned to the model with the new crash trace.

### Stage 5: Multi-candidate ensemble selection

Empirical research from AIxCC proves that generating multiple distinct patch candidates ($N=3$) and comparing them outperforms any single-shot generation.

When three independent candidates pass automated testing, the harness ranks them using structural contrast:
- A patch that adds 45 lines of nested conditions across three files is down-ranked.
- A concise, targeted 4-line patch that fixes the root-cause calculation is prioritized.

## Canary deployment and automated rollback gates

Once a patch clears the closed-loop verification pipeline, it moves to deployment behind automated rollback gates:

1. **Shadow traffic routing:** The patched microservice receives a mirrored stream of live production traffic without serving user-facing responses.
2. **Metric baselines:** Telemetry tracks P99 latency, heap allocation growth, CPU utilization, and unhandled exception rates against the baseline service.
3. **Automated rollback:** Any latency increase exceeding 5%, memory growth indicating a resource leak, or shift in status code distributions triggers an immediate rollback.

The failure signature and memory dump are automatically captured and routed back to the synthesis loop as negative constraints for the next iteration.

---

## Architectural takeaways for systems engineers

1. **Never trust a passing unit test.** Standard test suites do not test the edge cases exposed by zero-day vulnerabilities. Passing tests indicate syntax validity, not semantic correctness.
2. **Enforce observational equivalence.** Dual-execution testing against recorded benign traffic is the single most effective defense against domain truncation and accidental regressions.
3. **Direct fuzzing at the diff.** Seed fuzzers with the original exploit and target the modified basic blocks under ASan and UBSan to expose incomplete guards.
4. **Use candidate ensembling ($N=3$).** Generating three diverse candidates and selecting the cleanest root-cause fix significantly outperforms single-shot generation.
